Welcome to Sanaspace Hospital Database Application

A Spring Boot application for managing hospital data.

Overview

The Sanaspace application is a RESTful API built with Spring Boot, designed to manage hospital-related data including doctors, patients, medications, insurances, prescriptions, and visits. The application also includes a console UI for interacting with the system.

Object-Oriented Programming Principles

Abstraction

The application uses abstraction to hide complex implementation details:

  • Entities abstract database tables using JPA annotations
  • Services provide clean interfaces for business logic
  • Controllers abstract HTTP request handling
  • The ConsoleUI class abstracts user interaction details

Encapsulation

Data and behavior are encapsulated throughout the application:

  • Entity fields are private with public getters/setters (via Lombok)
  • Service classes encapsulate business logic
  • The LoggerUtil encapsulates logging functionality
  • EntityLookup encapsulates entity-specific display logic

Inheritance

The application leverages inheritance in several ways:

  • Repositories inherit from JpaRepository
  • Custom exceptions inherit from RuntimeException
  • The ServiceRouter inherits behavior from CommandLineRunner
  • Entities could share a common base class (though not currently implemented)

Polymorphism

Polymorphism is used extensively:

  • Generic repository methods work with any entity type
  • ApiResponseUtil handles responses polymorphically
  • The handleOperation method in services uses SupplierWithException
  • EntityLookup uses functional interfaces for polymorphic behavior

Models (Entities)

The models represent the core data structures persisted in the MariaDB database. Each model corresponds to a table:

  • Doctor: Represents a doctor with attributes like firstName, lastName, email, specialization, and experience
  • Insurance: Represents an insurance company with companyName, address, and phoneNumber
  • Medication: Represents a medication with name, sideEffects, and benefits
  • Patient: Represents a patient with firstName, lastName, email, phoneNumber, and optional insurance
  • Prescription: Links a patient, doctor, and medication with prescription details
  • Visit: Represents a patient-doctor visit with a composite key

Controllers

Controllers handle HTTP requests and map them to service layer operations:

  • CDoctor: Manages doctor-related endpoints
  • CPatient: Manages patient-related endpoints
  • CMedication: Manages medication-related endpoints
  • CInsurance: Manages insurance-related endpoints
  • CPrescription: Manages prescription-related endpoints
  • CVisit: Manages visit-related endpoints
  • CAnalytics: Provides dashboard statistics

Services

Services contain business logic and interact with repositories:

  • SDoctor: Handles doctor operations with validation and logging
  • SPatient: Handles patient operations with validation and logging
  • SMedication: Handles medication operations
  • SInsurance: Handles insurance operations
  • SPrescription: Handles prescription operations
  • SVisit: Handles visit operations with composite key support

Repositories

Repositories provide data access using Spring Data JPA:

  • RDoctor: Doctor entity repository
  • RPatient: Patient entity repository
  • RMedication: Medication entity repository
  • RInsurance: Insurance entity repository
  • RPrescription: Prescription entity repository
  • RVisit: Visit entity repository with composite key support

Database Schema

The application uses a MariaDB database with the following tables:

  • doctors: Stores doctor details
  • insurances: Stores insurance company details
  • medications: Stores medication details
  • patients: Stores patient details
  • prescriptions: Stores prescription details
  • visits: Stores visit details with composite keys
