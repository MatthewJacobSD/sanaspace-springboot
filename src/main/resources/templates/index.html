Welcome to Sanaspace Hospital Database Application

A Spring Boot application for managing hospital data.

Overview

The Sanaspace application is a RESTful API built with Spring Boot, designed to manage hospital-related data including doctors, patients, medications, insurances, prescriptions, and visits. Below is a detailed description of the application's components and how they implement key OOP principles: polymorphism, abstraction, inheritance, and encapsulation.

Models (Entities)

The models represent the core data structures persisted in the MariaDB database. Each model corresponds to a table: doctors, insurances, medications, patients, prescriptions, and visits.

  • Doctor: Represents a doctor with attributes like firstName, lastName, email, specialization, and experience. Uses enums for specialization and experience.
  • Insurance: Represents an insurance company with companyName, address, and phoneNumber.
  • Medication: Represents a medication with name, sideEffects, and benefits.
  • Patient: Represents a patient with firstName, lastName, email, phoneNumber, and optional insurance.
  • Prescription: Links a patient, doctor, and medication with details like dosageAmount and prescriptionDate.
  • Visit: Represents a patient-doctor visit with a composite key (patientId, doctorId, visitDate) and attributes like symptoms and diagnosis.

OOP Principles:

  • Encapsulation: Attributes are private with public getters and setters (via Lombok's @Getter and @Setter). For example, Doctor's email is validated with @Email.
  • Abstraction: Entities abstract database tables using JPA annotations like @Entity and @Column, hiding database complexity.
  • Inheritance: Not explicitly used among entities, but JPA's @Inheritance could be applied if entities shared a common fields (e.g., a base Person for Doctor and Patient).).
  • Polymorphism: Relationships (e.g., @ManyToOne in Prescription) allow flexible interactions. For instance, a Prescription can reference any Doctor or Medication.

Controllers

Controllers handle HTTP requests and map them to service layer operations. Each entity has a dedicated controller (e.g., CDoctor, CPatient) implementing RESTful CRUD operations.

  • Endpoints: GET, POST, PUT, PATCH, DELETE for each entity (e.g., /api/doctors, /api/patients/{id}).
  • Example: CDoctor: Manages doctor-related endpoints with logging and validation.

OOP Principles:

  • Encapsulation: Controllers encapsulate request handling logic, exposing only REST endpoints.
  • Abstraction: Use @RestController and @RequestMapping to abstract HTTP handling.
  • Inheritance: Controllers inherit from Spring's framework classes indirectly through annotations.
  • Polymorphism: Generic ApiResponseUtil handles responses for all controllers, allowing polymorphic responses.

Services

Services contain business logic, interacting with repositories to perform CRUD operations. Each entity has a service (e.g., SDoctor, SPatient).

  • Example: SDoctor: Handles saving, fetching, updating, and deleting doctors with exception handling and logging.

OOP Principles:

  • Encapsulation: Business logic is encapsulated within service methods, accessible via public interfaces.
  • Abstraction: Services abstract database operations, providing a clean interface for controllers.
  • Inheritance: Services leverage Spring's dependency injection, inheriting behavior from @Service.
  • Polymorphism: The handleOperation method uses a generic SupplierWithException for flexible operation execution.

Repositories

Repositories provide data access using Spring Data JPA, extending JpaRepository for each entity (e.g., RDoctor, RPatient).

  • Example: RDoctor: Provides CRUD operations for the doctors table.

OOP Principles:

  • Encapsulation: Database queries are encapsulated within repository interfaces.
  • Abstraction: JpaRepository abstracts SQL queries, exposing only method signatures.
  • Inheritance: Repositories inherit CRUD methods from JpaRepository.
  • Polymorphism: Generic repository methods work with any entity type.

Database Schema

The application uses a MariaDB database with the following tables:

  • doctors: Stores doctor details (20 records).
  • insurances: Stores insurance company details (5 records).
  • medications: Stores medication details (37 records).
  • patients: Stores patient details (30 records).
  • prescriptions: Stores prescription details (40 records).
  • visits: Stores visit details with composite keys (50 records).
